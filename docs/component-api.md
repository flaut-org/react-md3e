# Component API policy

Status: Button, IconButton, AppBar, Dialog, List/ListItem, Checkbox, Radio/RadioGroup, Avatar, TextField, Autocomplete, Popover, Surface, Shape, and Card are implemented. See their API documents in `components`.

## Familiar conventions

Use familiar MUI conventions when they fit the component's Material 3 behavior: `children`,
`disabled`, `size`, controlled/uncontrolled state pairs, refs, slots, and callbacks. Preserve useful
semantics deliberately rather than importing MUI types as the public API.

Base UI stays behind our API. Its event details, part composition, and DOM attributes are
implementation choices unless a component explicitly exposes them.

No promise is made that every MUI prop, callback reason, DOM selector, or slot remains
interchangeable. Document accepted differences and update the consumer explicitly.

## Native MD3 Expressive values

When Material 3 differs from Material 2, use native MD3 names and values. For example, button design
uses the relevant MD3 appearances such as `filled`, `tonal`, `outlined`, `text`, and `elevated`, as
supported by the component specification.

Do not introduce `contained` as an alias for `filled`, or automatically map `h1` through `h6` to MD3
typescale roles. Typography appearance should use MD3 roles; HTML heading semantics are selected
independently. Individual names and complete prop unions remain to be designed.

State behavior needs the same care. Controlled values, defaults, keyboard changes, commit/change
events, and dismissal reasons must be specified before implementing a family. Autocomplete and
slider migration must preserve the consumer's required behavior even when an old prop name is
intentionally changed.

## Styling and structure

Component implementation files use `component-name.component.tsx` in an ownership tree. Private
children live in subdirectories; components shared by multiple parents live at the top component
level. Styles/types stay with their component, contexts go in `contexts`, and tests in `tests`.
Only intentional public boundaries need an `index.ts`. See [component structure](component-structure.md).
Framework-reserved filenames such as Next.js `page.tsx` and `layout.tsx` retain their names.

`className` and appropriate DOM props are expected composition points. `sx` is optional. Colocated
static styles are an accepted integration path. Polymorphism and slot support must have a documented
type and RSC serialization model.

Do not reproduce `.Mui*` classes or MD2 DOM structure as a hidden compatibility promise. Selectors
tied to the old structure should be migrated in the consumer.

## Accessibility and motion

Use native HTML where it provides the required semantics. Use Base UI for applicable interactive
patterns, and verify focus, keyboard, accessible names, touch behavior, and controlled state at our
public component boundary.

Use official MD3 visual references together with web accessibility patterns. Android code is a
reference for appearance and tokens, not a direct substitute for browser interaction rules. Define
reduced-motion and forced-colors behavior where relevant.

## Component readiness

A component becomes public when its API is documented, its CSS is generated by the accepted
pipeline, its module boundary is verified, and its relevant behavior is tested. Track homepage
integration in `migration/homepage.md` instead of creating a global wish list.
